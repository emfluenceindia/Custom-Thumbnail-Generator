## Feature context

Administrators must be able to create WebP derivatives from existing thumbnail files in two scopes: all existing thumbnail sizes for all eligible image attachments, or one selected thumbnail size across eligible image attachments. Supported source formats are JPEG/JPG, PNG, and GIF. The later UI milestone will call the backend in bounded per-attachment requests and display live progress.

This milestone implements the secure backend operations that the next milestone can call. Do not build or change admin buttons, progress UI, or front-end JavaScript yet. Do not regenerate missing thumbnails: this feature converts existing thumbnail files only.

## Scope

Add the smallest backend/API layer consistent with the existing `CTGEN_` class, AJAX, nonce, and capability patterns. The interface must let the future UI:

1. Obtain the eligible image attachment IDs for a conversion run — the query must explicitly filter to image attachments (`post_mime_type => 'image'` or equivalent), unlike the existing unfiltered `ctgen_get_all_attachments` handler.
2. Request conversion for one attachment, either for all its existing thumbnail sizes or for one validated registered size slug.
3. Receive structured per-size outcomes and run-level counts that distinguish converted, already-current, skipped, and failed items, with actionable error messages that do not expose filesystem paths to unauthorized users.

Use attachment IDs and registered size slugs as inputs; never accept arbitrary client-supplied source or destination paths. Validate the request nonce (`ctgen_media_actions`) and `manage_options` capability on every privileged AJAX action, matching the existing handlers exactly. Confirm the target is an image attachment, resolve its existing metadata and files safely, and skip absent, unreadable, unsupported, or corrupt thumbnail files without stopping the rest of a run. Do not process the full-size original as if it were a thumbnail.

For `all_sizes`, inspect the attachment's existing `sizes` metadata and convert each actual thumbnail file represented there. For a selected size, validate the slug against sizes registered in WordPress (`wp_get_registered_image_subsizes()`, matching the existing validation pattern) and process only that size when a corresponding existing thumbnail file is present. Do not create files for missing sizes. Include core, theme-registered, and plugin-registered sizes wherever they are represented in attachment metadata.

Call the milestone 1 converter directly; do not fork or duplicate its logic. Keep each request bounded to one attachment so the browser can sequence work and report progress. The ID-discovery endpoint should return only image attachments eligible for this operation and should not accidentally include documents or non-image attachments — verify this against a media library that actually contains non-image attachments (e.g. a PDF), not just against an all-image library.

WebP files are sidecar derivatives of the existing thumbnails. Preserve each source thumbnail and the attachment's original file. Do not change attachment metadata, post metadata, attachment URLs, or the original attachment format. Keep output naming stable on retries, use the collision/failure policy from M1, and make repeated runs safe and predictable. Never claim an item converted unless the output exists, is readable as WebP, and has valid dimensions/MIME information — do not infer success merely from the converter call returning without a PHP error.
