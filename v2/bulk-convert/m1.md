## Feature context

The complete feature will let an administrator convert existing image thumbnails to WebP, either in bulk across available thumbnail sizes or for one selected size. Supported source formats are JPG/JPEG, PNG, and GIF. Later milestones will add the bulk and per-size buttons, AJAX orchestration, and a real-time progress bar following the existing thumbnail-regeneration UI.

This is milestone 1 of 4. Build only the reusable server-side conversion foundation that later milestones can call. Do not implement bulk processing, AJAX endpoints, admin UI, upload-time conversion, or replacement of attachment originals/URLs in this milestone.

## Scope

Implement the smallest maintainable service/helper that converts one explicitly supplied eligible image file to a separately named WebP file. Design its interface so a future caller can pass an existing thumbnail's file path and a controlled destination path without the service needing to know about bulk loops, attachment queries, or UI state.

The converter must:

- Accept JPEG (including `.jpg` and `.jpeg`), PNG, and GIF sources; determine eligibility from validated image/MIME information (e.g. `wp_check_filetype_and_ext()` / `getimagesize()`-backed checks), not the filename extension alone.
- Use WordPress's image-editor APIs (`wp_get_image_editor()`) and verify that the *active* editor instance can actually produce `image/webp` before attempting conversion. Return a clear failure when the file, editor, source format, or WebP output capability is unavailable; do not silently fall back to another format, and do not infer WebP support merely from the PHP runtime (see Boundaries).
- Write a WebP derivative without modifying or deleting the source. Never allow the destination to resolve to the source path (compare resolved/realpaths, not raw strings, if symlinks are realistically reachable through the service's inputs). Define and document one deterministic behavior for an existing destination (stable overwrite, or deterministic non-growing suffixing) so retries never create unbounded duplicate filenames and never overwrite an unrelated file.
- Return a predictable success result containing at least the generated file path, width, height, and MIME type, or a useful `WP_Error` (or the repository's established equivalent) with a specific, actionable error code per distinct failure category — not one generic message for every failure.
- Handle failed/partial writes without ever reporting success or leaving a corrupt/zero-byte/truncated output file behind. Do not delete a previously valid destination as "cleanup" for a failed attempt that targeted the same path.
- Avoid silently flattening an animated GIF. Preserve animation only if the selected WordPress image editor demonstrably supports it (verify this against the actual editor instance in this environment, not documentation or assumption); otherwise reject/skip that input with a clear, specific failure reason distinguishing it from a generic conversion failure.

Do not update attachment metadata or change which file WordPress serves. Keep the original and its existing metadata usable throughout this milestone.

## Testing checklist — exercise every case and report pass/fail with evidence

For each item, state pass/fail and exactly how you verified it (automated test name + output, or the exact manual/`wp eval-file` steps and observed result). Do not summarize multiple cases as "tested various formats" — report each one individually.

1. Convert a valid baseline JPEG (`.jpg`) → succeeds; output is a genuinely valid WebP file (verify by reading it back with the image editor or `getimagesize()`, not just checking the file exists); reported dimensions and MIME match the output.
2. Convert a valid JPEG saved with a `.jpeg` extension → succeeds identically to case 1, confirming detection is MIME-based and not extension-based.
3. Convert a valid JPEG whose extension is deliberately wrong (e.g. a real JPEG renamed to `.png`) → confirm the service still correctly identifies it as JPEG via MIME/content sniffing rather than trusting the extension, or explicitly documents why it rejects mismatched-extension input.
4. Convert a valid PNG, including one with an alpha channel → succeeds; confirm transparency is preserved if the active editor supports it, or the limitation is explicitly and accurately reported if not.
5. Convert a valid static (single-frame) GIF → succeeds.
6. Convert a valid animated (multi-frame) GIF on an editor that demonstrably supports animated output → animation is preserved; verify the *frame count* of the output (not merely that a file was written) matches expectations.
7. Convert the same animated GIF on/with an editor path that does **not** support preserving animation → conversion is rejected/skipped with a clear, specific failure reason; confirm no silently-flattened single-frame WebP is produced.
8. Attempt to convert a file with an unsupported MIME type (e.g. BMP or TIFF) → clear, specific failure; no output file created.
9. Attempt to convert a corrupt/truncated file that has a plausible extension/MIME sniff but fails to load in the image editor → clear failure; no partial/corrupt/zero-byte output left behind.
10. Attempt to convert a non-existent source path → clear failure; no PHP warning/notice/fatal error surfaces.
11. Attempt to convert an unreadable source (permissions denied, if safely simulatable in this environment) → clear failure, not a fatal error.
12. Verify behavior when the active WordPress image editor cannot produce `image/webp` — force or locate an editor/environment path where this is genuinely true, rather than assuming GD/Imagick support; confirm the service checks actual editor output capability and fails clearly rather than assuming support because the PHP GD/Imagick extension is merely loaded.
